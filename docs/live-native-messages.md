# Private native-message smoke check

Run `node scripts/live-native-messages.mjs --provider codex --model MODEL --effort low --timeout 120` explicitly to use an installed, signed-in CLI. The check consumes model quota. Select a model available to your account; the override applies to this disposable board only.

Add `--column-automation --busy-queue` for the opt-in Codex busy-queue check. It sends a fixed longer message through the configured deferred row, observes that exact native turn working, then deliberately pastes one small manual follow-up and presses the default Tab queue key. It never clears the manual-input guard. Codex 0.157.0's default [composer binding](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/tui/src/bottom_pane/chat_composer.rs) and [input dispatch](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/tui/src/chatwidget/input_flow.rs) separate queued input from submitted input that can steer ongoing work. This diagnostic does not change the product adapter, user key bindings, provider flags or permission mode. Other CLI versions or custom bindings may fail the check; failure cannot authorize a different key or an automatic retry.

Queue success requires `busy.observed`, `queuedBeforeCompletion`, `firstReplyComplete`, `exactNextInput`, `sequenceValid`, `nextReplyComplete` and `manualInputObserved` to be true, with `interrupted` false and the existing prompt/Git/shutdown checks passing. The first reply must contain all 160 ordered fixed lines and its final marker. Matching numeric prefixes are accepted; missing, repeated or reordered lines are refused. Native history must show completion of that turn before a different turn starts with the exact follow-up and completes its exact reply. Both current `response_item` input-text and `user_message` records are supported. Steered input on the same native turn, aborts, wrong identities, changed history, errors and silence cannot establish success. The reader bounds files to 4 MiB and complete lines to 1 MiB, verifies append-only file identity and never includes conversation text or IDs in its report.

This mode requires Codex and `--column-automation` before creating any fixture. It shares the existing overall 1–180 second budget and owned cleanup. A completed first reply before the queue key causes a reported failure without pressing Tab. A failure after paste leaves the owned process for normal cleanup and never clears or resubmits its draft. This verifies manual native queue behavior in the disposable harness; automatic immediate/slash/exit messages and native-resume delivery remain pending.

The script creates its own repository and data directory, saves one fixed task in To Do, starts Executing and waits for a completed native turn. It moves to Code Review through the common lifecycle and checks the continued run ID. A private journal intent then sends one small literal deferred message and records native confirmation separately from the submission marker and durable journal receipt. By default this remains an internal transport check. Add `--column-automation` to configure a real deferred Code Review enter row instead; the Board move schedules delivery and the report records placement separately from its journal input receipt.

The JSON report contains readiness, observed native identity as a boolean, continued-run identity as a boolean, message/receipt status, exact saved prompt, clean main/worktree checks and owned-process shutdown. A confirmed receipt proves input, not completion of the second reply. A blocked startup or unconfirmed message is a reported result, not a passing check just because the script exits normally. No raw terminal output or conversation IDs appear in the report.

`--answer-trust` answers only the fixed disposable-folder and existing-hook-review startup questions. It never approves a tool call or clears manual-input observations. For Claude, the harness reads the current terminal viewport rather than stripping accumulated output, waits for a settled menu before Down, and verifies a settled current “Yes, I trust this folder” before Enter. Startup redraws restart the wait. A reset to No, an unsupported menu or lost/truncated output never grants confirmation or a blind repeated arrow. This applies only to the owned disposable live fixture; the product does not answer trust prompts automatically. `--fresh-trusted` optionally stops/resets the warmup through To Do and starts a separate conversation in the same already trusted worktree when the completed warmup observed startup input. The new process must establish its own readiness. The warmup receives no private message, and no unknown write is retried. The whole check shares the selected 1–180 second budget; The harness observes message delivery for at most ten seconds. A configured row retains the scheduler’s own bounded budget and is cancelled during cleanup if still pending.

`--keep` retains the owned fixture and reports its paths for local diagnosis. Otherwise cleanup removes both temporary directories after shutting down the private dispatcher, Board automations and Supervisor. SIGINT/SIGTERM cancel startup or private delivery, then use the same owned-process cleanup before reporting. The script does not edit a user repository, CLI credential file or global settings file. Native startup answers can cause the CLI to persist its own folder-trust records for the disposable path; cleanup leaves those CLI-managed preferences to the CLI. Kanban permission modes, ambient CLI tools and Base behavior are unchanged.

The offline test installs a simulated Claude-compatible executable in its own temporary PATH, runs this exact script through an actual owned PTY, checks exact delivery and cleanup, and uses no model or credentials. Invalid provider, timeout, model and effort options are rejected before filesystem setup or CLI launch.
