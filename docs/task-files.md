# Task attachments and file references

New task and Backlog editors accept file selection, pasted images and dropped files. Attachments are separate from the literal prompt: saving and To Do promotion never start agents, and unchanged textarea text retains its original CRLF bytes. Attachment assignments survive copying, Backlog promotion and restart.

Each task accepts 20 attachments, at most 4 MiB per file and 24 MiB total. Files are stored privately beneath the application data directory, scoped to the owning project and verified by SHA-256 on every read. Filenames cannot contain path components, control characters or Windows reserved names. Symlink, nonregular and hard-linked attachment files are refused. Uploads are immutable; altered stored bytes must be restored or reattached under a new filename, and are never silently overwritten. Removing a chip removes the assignment, not shared bytes. Preview detects supported raster image signatures; other files download as binary with their original names. The browser never renders uploaded HTML or SVG.

Type `@` in a prompt to select a project file or folder with the arrow keys and Enter, or use the project-relative reference field. References use the existing Files viewer boundaries: the explicitly linked folder, mapped into the task's registered worktree at execution. Absolute paths, traversal, symbolic links, Git internals and credential filenames are refused. References describe current workspace paths, not a snapshot of their contents. A reference unavailable in the task worktree must be restored or removed; it is never silently omitted.

Attachment and reference edits increment the task content revision and invalidate earlier plan/review evidence. Pause active or queued agents and finish pending automations before changing their files. Agent preparation validates every file again and appends absolute paths through the existing prompt renderer. Base delivery and ambient CLI configuration are unchanged. Missing or altered attachments fail explicitly before process launch; no fallback run is started.

GitHub issue imports can capture Markdown/HTML inline images. The picker explicitly offers a text-only alternative. Image capture accepts public GitHub user-attachment URLs and GitHub image hosts, pins public DNS addresses and revalidates each redirect. No cookies or authorization are forwarded. Downloads share a 30-second import budget, have a 24 MiB aggregate limit per selected import and allow only PNG/JPEG/GIF/WebP responses. Private, unavailable or unsupported images abort the entire draft/label/ledger publication; import without images and attach them manually. Duplicate imported issues do not redownload images. Exact issue text, including its original image links, is preserved.

Portable backups with files use version 11 and carry attachment bytes with verified descriptors and project ownership; boards without files continue exporting version 10. Portable attachment bytes are limited to 24 MiB per backup. Missing or inconsistent bytes reject import before board publication. Project-relative references remain inert until their repository is explicitly linked; machine-specific absolute paths, runs and workspaces are never imported. State version 13 preserves version 12 source catalogs, import ledgers, sessions, Base and user extensions during migration.

Attachment upload/read/reference routes require the existing local page token and origin checks. Older servers hide the new controls through the `taskFiles` capability. Uploads do not write cards or start agents. Detached upload bytes are retained; cleanup remains a separate approved task.
