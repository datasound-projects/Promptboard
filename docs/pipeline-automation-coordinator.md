# Ordered automation groups

`PipelineAutomations` combines the prepared move journal and execution adapters for one exit or enter group. The [column runtime](pipeline-runtime-automations.md) now connects scripts/webhooks to board transitions, task-scoped cancellation and authenticated receipt endpoints. The [editor](pipeline-automation-editor.md) and [notification receiver](pipeline-notifications.md) expose those actions; the native message scheduler remains pending. Composer, Base delivery and native CLI configuration retain their existing paths.

The caller records the move first, runs its exit group, applies and records the session lifecycle, then runs its enter group. The coordinator verifies row order, IDs and normalized configuration hashes against that move before any action starts. It also checks task/project identity and derives source/destination column variables from the journal. Metadata is captured once so a later mutation cannot rewrite an in-flight template. The caller remains responsible for task/configuration revision guards, verified workspaces and native session ownership.

Every eligible row receives a durable start grant before dispatch. Webhook attempts save their own receipts before transport. Disabled rows remain skipped. Normal row failures do not stop the group: exit failure can still allow the lifecycle to proceed. If script termination remains unconfirmed, later rows are skipped, advancement is refused and the group retains ownership so Cancel/shutdown can retry stopping the script. The caller must honour `safeToAdvance`; it must not apply a lifecycle after cancellation or unconfirmed cleanup.

An exit group has one sixty-second soft budget, including waits and retries. Each adapter receives the remaining budget; timeout skips rows that have not started. Owned script termination can require the adapter's bounded cleanup grace before the group returns. Enter rows retain their adapter limits. Message callbacks have a maximum 150-second acknowledgement budget, configurable downward for fixtures. A message callback must respect its cancellation signal before actual submission; this service cannot make an arbitrary callback cancellation-safe.

Accepted groups, action adapters and message acknowledgements own referenced deadline timers, cleared on completion. This keeps a pending callback alive until its bounded outcome is available on Node 22, where an unreferenced `AbortSignal.timeout` alone permits process exit. A standalone-process notification regression verifies the adapter without a test keep-alive interval. The coordinator also rechecks the monotonic exit budget immediately before dispatch after persistence/display work.

One coordinator owns one `PipelineActions` instance and its lifetime. Groups for different tasks can proceed independently. A duplicate active request shares the original promise; a completed request returns recorded outcomes and grants no further lifecycle advancement. An unfinished prior group is refused rather than resumed after a lost outcome save. A different move on the same task is refused while the group or an unresolved owned script remains active. The board integration must cancel a superseded group before waiting for task locks and validate the replacement against current state.

Agent messages require an injected session service. The synchronous `deliverMessage` callback receives literal rendered text, action/task/project IDs, trigger and immediate/deferred mode. Only explicit `confirmed: true` records success; scheduling, echo or an absent acknowledgement is unconfirmed. Exit messages retain this confirmation requirement. Cancellation and timeout cannot be replaced by a late acknowledgement. A manual column or restore can suppress messages while leaving non-message rows eligible. Without a suitable service, eligible enabled message rows are rejected before mixed-group effects begin.

An optional `scheduleEnterMessage(request, { signal })` callback supplies asynchronous enter handoff without waiting for a fresh agent that the caller has not started yet. It receives the same fields plus a separate copied `key` containing the project, task and transition IDs. Before acknowledging, the callback must durably call `journal.scheduleMessage(key, actionId, { provider, sessionId, runId, mode, messageHash })`, using SHA-256 of the exact rendered UTF-8 message. Its reply must contain `scheduled: true` and that exact provider/session/run tuple. The coordinator rereads the original journal key and verifies scheduled action status, message hash, mode and tuple. A mere scheduling or delivery claim cannot fabricate durable handoff.

Verified handoff leaves the action `scheduled` and its separate delivery receipt pending. The caller can finish placement and release fresh startup only after a successful group with `safeToAdvance: true`. The scheduler must later acquire the journal's one native dispatch grant, record submission, and separately establish native queue acceptance or conversation confirmation. Placement completion and callback `confirmed: true` never confirm delivery. Both immediate and deferred messages use this handoff; their distinct readiness rules belong to the session scheduler.

Every ordinary action outcome must also receive a true journal save acknowledgement. A persisted queue with a lost, cancelled, timed-out or mismatched callback acknowledgement cannot be overwritten as a normal failure: the group throws `AUTOMATION_OUTCOME_UNSAVED`, starts no later row and authorizes no lifecycle advancement. The caller must stop and record its owned scheduler work before cancelling the move; a duplicate group cannot replay that intent. A callback that has not persisted a queue instead receives a normal unconfirmed/cancelled/timed-out outcome. Once that outcome is saved, a late callback cannot acquire a scheduling grant. Callers must honour thrown errors as well as `safeToAdvance` and cancellation signals.

This module does not start an agent, choose a native conversation or implement immediate/deferred readiness. The optional handoff is a tested integration contract, not a connected native scheduler. Its caller remains responsible for FIFO ordering, exact process/session/workspace/Base ownership, verified empty-input readiness, permission waits, human draft protection, cancellation/recovery and native confirmation. The board does not inject this callback and still refuses enabled message rows. Explicit delivery retries and receipt UI remain pending. The optional progress callback supplies text metadata after the start is saved; display failures cannot erase intent or stop execution.

Tests use actual journal files and execution adapters with injected notification/message/HTTP receivers. They verify persisted intent and webhook attempts before effects, order, failure isolation, the aggregate exit deadline, independent cancellation, shutdown, manual/restore suppression, literal templates, strict confirmation, late acknowledgements, storage failure, incomplete-group replay refusal, unresolved script ownership, metadata identity and mutation, and progress failures. No live agent, external webhook or desktop notification is used.
