# Shared task labels

Pipeline tasks now expose Kangentic's [shared labels and custom colors](https://www.kangentic.com/guide/creating-tasks/) through task checkboxes and a project label editor. Names and colored indicators appear on active cards, Done previews, completed rows and task details. Text remains readable without relying on color. The [local backlog foundation](local-backlog.md) shares these definitions and retains assignments on To Do promotion; its app view and active-column/import integrations remain pending.

The board and completed table share a keyboard-accessible Label filter: All labels, Unlabeled or one project label. Label and priority filters combine; completed title or exact `#number` search and sorting still apply. Preferences stay in this browser per project. Filtering changes no task, agent, Base, session or saved order. Done applies both filters before the five-card preview limit. Keyboard moves resolve visible neighbors against the complete saved column, preserving hidden tasks; completed selections remain selected when filtered out. Renaming a label retains the filter's stable ID and refreshes its name. Removing the selected definition resets both views to All labels. Malformed/foreign preferences, legacy projects and older capabilities show all labels; Timeline remains unfiltered.

Manage labels on the board or inside a card editor. Add labels, edit their names and hex colors, or remove definitions; Save labels publishes the shared catalog. Card checkboxes preserve assignment order and bind their save to the catalog they displayed. A nested catalog save preserves the unsaved card title/body and updates the displayed choices. Removing an assigned label refreshes only the known resulting metadata revision; concurrent task text, priority or settings changes retain the stale-card refusal. A stale catalog keeps its draft and offers explicit Reload labels. Updating shared colors/names also refreshes an open completed table without changing task content or agent execution. The server advertises `taskLabels`; older sessions hide these controls and omit the unsupported fields.

Each project owns up to 100 label definitions with a stable ID, a trimmed Unicode name of up to 60 characters and a six-digit hex color. Names are unique after NFC normalization and conversion to lowercase within the project. IDs are unique within the project. Up to 20 distinct label IDs can be assigned to a task. Unknown or cross-project IDs, controls, malformed Unicode, arbitrary CSS values and duplicate definitions or assignments are refused.

`PATCH /api/projects/:id/labels` replaces the catalog using `labels` and `expectedLabelRevision`. Its independent label revision starts at zero and increments only when definitions change. It leaves the project configuration revision unchanged. Recoloring or renaming a label therefore updates the shared definition without changing cards, prompts, agent settings, Base delivery, task order, session state or pending automation messages. Removing a label removes only that ID from assigned cards, increments those cards' metadata revisions and keeps their content revisions and execution intact. A no-op catalog save retains label and card revisions; the Store still publishes its normal successful-update revision.

Task creation and editing accept `labelIds` with the current `expectedLabelRevision`. Edits also retain the normal card revision guard. Stale catalogs and cards refuse the edit rather than applying another label or overwriting newer assignments. Omitted label fields preserve existing assignments during ordinary edits. Composer and split-task creation default to an empty assignment and continue placing exact text in To Do without starting agents. Copies, common column moves, archive and restore retain assignments.

State version 10 introduced an empty catalog, independent label revision and empty task assignments for older state. Migration retains identities, task numbers, priorities, prompt bytes, native references, Base, pending messages and extensions, and preserves an exact pre-migration file. Current state version 11 also retains local backlog metadata; future versions are refused unchanged. Portable backup version 8 introduced label definitions and assignments; current version 9 also carries backlog drafts, and versions 1–7 import without labels. Malformed label metadata rejects the entire import before publication. Label import never supplies native session grants or enables execution.

Offline checks exercise authenticated HTTP authoring, stale revisions, malformed and foreign IDs, recoloring/removal, exact migration and atomic portable import. A configured deferred column message remains queued through catalog/assignment edits, then confirms once its same owned run becomes ready. Real-browser checks cover keyboard assignment and catalog editing, both themes and desktop/phone widths, escaped labels, nested drafts, own removals, concurrent edit refusal and older capability sessions. Filter regressions cover combined label/priority/search, archive selections, visible-neighbor reordering, project/reload preferences, rename/removal and malformed preferences without agent work. Provider startup/resume and future backlog behavior are not certified by these checks.
