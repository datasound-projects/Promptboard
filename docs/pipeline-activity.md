# Pipeline activity observations

Pipeline runs now keep activity separately from their process status. Cards and the terminal dock show outstanding tools, subagents, native background tasks, scheduled wakeups and permission waits where the provider reports them. A finished parent response can coexist with outstanding work. A subordinate response or failure does not complete or fail the parent run.

Claude pipeline sessions add observation hooks for tool start/success/failure/denial and subagent start/stop. Tools use native IDs scoped to their subagent; repeated completion IDs cannot decrement another tool. Native Stop/SubagentStop background and scheduled-work snapshots contribute counts only. A requested background operation without a subsequent snapshot remains uncertain. Gemini pipeline sessions add BeforeTool/AfterTool observations; calls without native IDs use per-tool outstanding counts. Codex's current notify integration reports completed turns only, so it cannot expose tool/subagent activity or permission waits. Missing observation capabilities are not supplied by guessing from terminal text.

The reducer's `ready` field requires a parent turn-end event, no observed permission wait or outstanding work, no uncertain counters, a live session, and 1.5 seconds of quiet after the latest event/output. Quiet output alone never establishes completion. Readiness describes the available observations, subject to the provider coverage shown in the snapshot; it is not proof that an unobserved external job has stopped. The supervisor’s current observations now gate [live same-provider settings handoffs](pipeline-live-settings.md). Saved snapshots do not authorize a restart. Activity does not deliver automation messages, approve work or automatically advance cards.

Counters are bounded. Pending partial hook records block readiness; malformed/truncated records, overflow and malformed subagent starts remain uncertain until explicit process suspension/resumption starts a new observation tracker. Background requests without snapshots remain uncertain until the provider supplies an authoritative background snapshot. Missing tool completions are not silently cleared by a timeout. Pause remains available. Restart recovery never uses a saved activity snapshot to launch or replay work.

The hook bridge stores bounded tool/subagent IDs and counts, without raw tool arguments/results, background commands or cron prompts. Approval metadata records the native result as a boolean without its plan path. It records approval evidence only for a successful main Claude `PostToolUse` of `ExitPlanMode`, or a Gemini `AfterTool` whose native `exit_plan_mode` result explicitly reports approval without an error. Requests, failures, subordinate plan tools and rejected/invalid Gemini plans do not count. Gemini rejection can have no error field, so successful tool completion alone is insufficient. These observations do not yet implement automatic plan moves. See the [Claude hooks reference](https://code.claude.com/docs/en/hooks), [Gemini hooks reference](https://geminicli.com/docs/hooks/reference/) and [Gemini native plan tool implementation](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/exit-plan-mode.ts).

Additional tool/subagent hooks are enabled only for pipeline runs. Legacy stage workflow, Composer input and selected Base plus inherited CLI tools remain intact. The bridge prints no hook decisions or injected instructions. Validation uses pure reducer cases, actual hook subprocess payloads, simulated providers in real PTYs and Chrome checks in both themes on a narrow viewport. It does not establish authenticated live-provider compatibility.
