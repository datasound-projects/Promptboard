# Private deferred native input

The [journal bridge](native-message-dispatch.md) can supply `confirmDelivery` to save exact native confirmation before this transport releases input. Only strict `true` acknowledges it; a failed, lost or cancelled save preserves uncertainty. This remains an internal callback, not connected column scheduling.

`Supervisor.sendNativeMessage` is an internal transport seam. It is not an HTTP action, a connected column scheduler, or permission to enable message rows. Column moves still refuse enabled agent-message automations. Composer tasks still enter To Do without starting a run, and the first task envelope, Base delivery and inherited CLI tools are unchanged.

The caller supplies a unique dispatch ID, literal rendered message, deferred mode and bounded cancellation/deadline. It must own task/settings preflight, scheduling, and the durable journal callbacks. `grant` must acknowledge persistence for the exact dispatch ID, message hash, provider, logical session and process run before any input. `submitted` records the one Enter attempt; `accepted` records a native queue receipt separately. Only strict `true` acknowledges a callback. The caller must save the returned delivery outcome before advancing its automation group. This seam does not connect those callbacks to the board journal.

The Supervisor obtains the actual run and retains its process ownership checks; request data cannot replace the owned session, run, lifecycle reader or ownership predicate. Transport waits for an independently observed completed, settled main turn with no outstanding work or permission wait, plus the owned terminal's enabled bracketed-paste mode and complete control sequence. Terminal output or silence alone never establishes readiness. Pending initial input, lifecycle uncertainty and any observed nonempty human input block this transport. A human draft is never cleared.

One process admits only one active attempt. Each valid dispatch ID is consumed once, including failed grants, with a bounded registry of 4096 IDs; exhaustion refuses further input rather than forgetting old attempts. The native-history checkpoint precedes dispatch. Literal UTF-8 code points and paste delimiters are preserved in bounded writes, followed by a separate Enter after a one-second spacing floor. The floor is input spacing, not submission evidence. Human input, a new main hook, changed paste mode, permission wait, lifecycle uncertainty or changed process/native identity cancels the remaining paste or Enter. No attempt sends Esc, clears a draft, restarts a CLI or retries unknown input.

Preparation, polling, event reads, receipt reads, persistence callbacks and outcome publication share one budget (at most 150 seconds). Cancellation or loss of process ownership bounds hanging callbacks. Late acknowledgements cannot revive a finished attempt. Callback work may finish later; the caller still owns its cancellation and durable reconciliation. The Supervisor retains its process lease through outcome publication; unknown publication blocks another request even when native input was observed.

An outer `TimeoutError` is a deadline: it returns `timed_out` before any terminal write and `unconfirmed` after input was attempted. Explicit cancellation remains `cancelled`. Both stop the attempt, publish fixed reasons without private error details, and never retry input; an unconfirmed write remains sticky.

Pending hook processing does not itself revoke ownership of the unchanged process. It does block readiness, every paste/Enter boundary and receipt confirmation. The transport drains owned hooks before reading a receipt and again after the asynchronous read, retaining the captured proof while an incomplete hook settles. Changed identity, uncertain lifecycle, process loss and cancellation still revoke the attempt. A hook that never settles reaches the same deadline without replay.

Confirmation requires an exact new user message in the owned native history. A Claude enqueue receipt is acceptance only, never a submitted turn or completed work. Submission markers alone supply no confirmation. Lost saves, changed history or unknown writes return fixed, non-sensitive reasons without replay. Any write without confirmation makes input uncertainty sticky for that process. Pending input hides readiness and blocks Stop-based completion and automatic plan routing; a later Stop cannot clear unknown input. A confirmed receipt proves input only: task completion remains dependent on independently observed main lifecycle events.

Immediate/busy delivery, slash commands, ill-formed Unicode, terminal control characters and messages over 64 KiB are unsupported before acquiring a grant. The implementation does not use Codex's separate queue command: its shared-server requirements are not ownership evidence for Promptboard's per-run process. Native pasted-content transformations and unsupported history formats remain unconfirmed rather than being matched loosely. Real provider queue behavior, durable scheduler integration, receipt display, explicit retry controls and enabled column rows remain pending.

Offline tests cover Claude/Codex/Gemini history formats through controlled process seams, partial Unicode/chunk boundaries, failed/lost grants, concurrent and repeated dispatch, cancellation, permission/mode/lifecycle changes, pending Stop and unknown submission saves. A disposable repository and actual PTY run a simulated Claude-compatible CLI for two successive exact messages, preserving the original Composer/Base input and CLI flags. These tests use no model, sign-in or quota and do not certify live provider behavior.

Reference behavior: [Kangentic columns and automations](https://www.kangentic.com/features/workflows/). Provider contracts: [Claude hooks](https://code.claude.com/docs/en/hooks), [Gemini hooks](https://geminicli.com/docs/hooks/reference/), and [Codex's queue command implementation](https://github.com/openai/codex/blob/b8dceb0d4f29e49e73daa08f57fcf5181186f354/codex-rs/tui/src/session_queue_commands.rs).
