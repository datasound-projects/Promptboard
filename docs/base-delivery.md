# Base delivery and verification

## Agents, Agent Profiles, Custom MD files and switches (2026-10-17)

- **Agents and Agent Profiles are different.** An **Agent** (stored kind `profile`) is one agent definition: provider, model, effort, permission, instructions and its own resources. An **Agent Profile** (kind `agentProfile`) composes a deployable setup: one **primary agent**, optional **supporting agents** (each with a responsibility and its own switch), equipped resources (MCP servers, skills, knowledge, context, tools, packs, Custom MD files) and profile instructions. It runs as its primary agent (`profileDefaults`: the agent's tuple, its instructions followed by the profile's, both delivered in the prompt); the primary agent's own resources come along, and agents nested in it become subagents as when it is assigned directly; supporting agents become native subagents only where the CLI supports them (Claude Code writing stages) and are kept but reported elsewhere. A profile without a switched-on primary agent cannot run (`BASE_PROFILE_NO_PRIMARY`). Both kinds can be the agent of a global, project or column target; an Agent Profile is never a resource of another resource, an Agent is one only as another Agent's subagent or as an Agent Profile's agent, and packs cannot contain either.
- **Shared, never copied.** Profiles, packs and assignments reference resources by ID. Editing a resource changes it everywhere it is used; **Used by** lists every place.
- **Switches at each level.** A resource's global switch (`enabled`) keeps its configuration and removes it from every future run. Every reference (in a binding, a pack, an agent profile) has its own optional `enabled: false` — switched off there only, recorded in the manifest as `disabled-here`, while other assignments keep it. An MCP server has server-wide **switched-off tools** (`disabledTools`), and a reference can switch off more for itself; the manifest carries the union.
- **MCP tools withheld per CLI.** Claude Code: `--disallowedTools mcp__pb_<id>__<tool>`, with the tool name written as Claude Code writes it (characters other than letters, digits, `_` and `-` become `_`, so `notes.delete` is `…__notes_delete`); Codex: `-c mcp_servers.pb_<id>.disabled_tools=[…]`; Gemini CLI: `excludeTools` in the per-run settings. Verified live with Claude Code (haiku): with the tool on, the agent listed `mcp__pb_<id>__read_document`; switched off for its profile, it listed none. Verified again on 2026-10-20 (Claude Code 2.1.304, haiku, through a Kanban run): of `notes.read` and `notes.delete`, with `notes.delete` off for the Agent Profile, the agent listed only `mcp__pb_<id>__notes_read`, and quoted the code word from the attached SOUL.md and its primary agent's instructions.
- **Custom MD files** (kind `markdown`): AGENTS.md, CLAUDE.md, GEMINI.md, SOUL.md, IDENTITY.md, MEMORY.md, USER.md, Copilot instructions, Cursor `.mdc` rules or any `.md` of your own (`SKILL.md` belongs in Skills). Each shows its convention and which CLIs read it natively from a repository (Codex reads AGENTS.md; Claude Code reads CLAUDE.md, and AGENTS.md only when there is no CLAUDE.md; Gemini CLI reads GEMINI.md, AGENTS.md only through `context.fileName`; SOUL/IDENTITY/MEMORY/USER are OpenClaw files no supported CLI reads by itself). **Attached, Promptboard sends the file in the prompt for every CLI** under its own name (verified live: the agent quoted a code word that existed only in the attached SOUL.md). Activation: Always, some projects, some stages, some CLIs, or On demand (sent only when attached to the task); an inactive file stays attached and is not a warning. A **project version** (`override: { of, projectId }`) replaces the shared file in that project only; it starts with the shared file's trust. A file's text is document content: an export without document bodies (and a board backup without Base content) leaves it out and the import marks the file omitted, as for skills and knowledge. **Write to a repository…** previews and then writes the file at its conventional path in a project folder, replacing an existing file only if it still matches the preview, and only for trusted files. Templates are plain, editable Markdown. **Restore this version** saves an earlier revision as a new one.
- **Imports.** *Import MCP servers…* reads Claude Desktop's configuration (or a pasted `mcpServers` / VS Code `servers` JSON from Claude Code, TRAE, Gemini CLI or Antigravity): secret values are never copied (they become environment-variable references to set), arguments that look like credentials and legacy SSE servers are refused (a server or command recipe created by hand is refused a new argument with a known token prefix, a `secret=value` shape, a password in a URL, a secret header such as `Authorization: Bearer …` or a value after a flag such as `--api-key` too, unless the secret part is a `$VAR` or `${VAR}` reference; arguments saved earlier keep loading), duplicates are recognised, and imported servers start switched off and untrusted. *Import Markdown from a repository…* finds known instruction files up to four folders deep (no links, no `node_modules`/`.git`), imports skills as skills, skips files already in Base, and starts files untrusted. Both are refused from a paired phone, and the Base page does not offer them there.
- **MCP discovery** keeps each tool's short description, read-only/destructive hints and required inputs (redacted, shown to the person only, never sent to an agent). A connection result is kept while the server's definition is unchanged (renaming or switching tools does not remove it) and removed when the definition changes.
- **Assignments.** In the Base picker of a project, column or card, and in a pack, every selected resource has its own on/off switch next to Required.
- **Origin** "Use in Kanban" can add Project Context to an agent profile's resources. Research's Base MCP sources read the server's current Base definition at each use. **Compose** still has no Base integration.
- **Flocker** ([flocker.md](https://flocker.md/)) offers agent profiles through a remote MCP server (`https://mcp.flocker.md/mcp`, OAuth) and a skill. It can be added like any Streamable HTTP MCP server; its OAuth stays with the CLI. Nothing in Promptboard depends on it.

## Agent profiles, native subagents, and avatars

Agents (stored kind `profile`) can equip every Base resource type except Agent Profiles, and other Agents, by reference. A profile selected in an existing agent configuration slot supplies same-scope defaults. Attaching another profile supplies a native subagent where supported; it does not switch the parent’s provider/model or grant that subagent new permissions. The shared resolver pins profile instructions and resources and rejects dependency cycles. Empty Replace opts out of inherited profiles/resources.

Native subagents currently use Claude Code’s documented interactive `--agents` JSON in writing stages. Descriptions, prompts, model IDs, and effort come from immutable profile definitions; permission mode inherits the parent, and Enter/Exit Plan Mode remain denied. Definitions are limited to 16 agents and 60 KB per run. Context is bounded and captured alongside the supplied manifest. MCP tools are inherited from the selected session’s configuration; this does not claim exclusive tools per subagent. Invocation remains the CLI’s decision and is not inferred from configuration. Other providers and Planning/Code Review report incompatibility, with required resources blocking launch. See [Claude subagents](https://code.claude.com/docs/en/sub-agents). Installed help checked: Claude Code 2.1.287; deterministic fixtures do not establish live delegation.

Avatar generation uses the [OpenAI Image API](https://developers.openai.com/api/docs/guides/image-generation) through an explicit action. The fixed HTTPS endpoint returns one bounded JPEG illustration draft. Default model: `gpt-image-2.5-flare`, override with `PROMPTBOARD_IMAGE_MODEL`; credential reference defaults to `OPENAI_API_KEY`, override the variable name with `PROMPTBOARD_IMAGE_API_KEY_ENV`. No credentials enter saved definitions, previews, exports, or diagnostics. Cancellation targets the avatar job and shares the existing job coordinator. Save the profile to keep its reviewed image; basic editing and placeholder portraits work without API access. Portraits never enter run prompts. Private document/portrait bytes require explicit export inclusion. No authenticated image generation was run during tests.

Connection tests and source refreshes publish new resource revisions. Save editor changes before either action; the editor reloads the current revision and results afterward, including failed connection tests. Refresh replaces only sources marked as managed refresh captures and preserves pasted/uploaded sources and wiki pages. Older captures without a refresh marker are retained as standalone sources, so upgrading cannot silently delete them. Pages retrieved from different knowledge collections have distinct source IDs while provenance retains the original collection and page IDs.

Base exports are checked compact against 12 MiB, and the page saves them compact; an import accepts a file whose compact JSON fits, with 1 MiB of request room left for the ID remap. A Base change that is not published (an import or backup that loses a race or fails validation, a conflicting save) removes the revision files it wrote, except files the registry or a run names. When a write meets a Base change from another window, the page reloads the library and sends it once more; resource and target revisions still refuse real conflicts.

Base definitions and assignment previews do not start programs. A normal Kanban run resolves the actual provider and column, pins immutable definitions, then prepares selected resources in the existing Supervisor before the CLI starts. Required failures stop launch; optional omissions appear in the manifest. Resource changes apply to future accepted runs. Current disablement, trust revocation, and deletion also block a queued snapshot from launching. Running CLI sessions are not reconfigured.

An available pack expands its members in declared order. Required packs make their members required; a member's own declared requirement is also retained. Dependency requirements propagate to a fixed point. A more-specific explicit selection can change an inherited requirement. Disabled or untrusted optional packs do not expand, while independently attached members can still be supplied. Excluding a pack excludes its members; a later scope may explicitly add one back.

## Delivery matrix

| Resource | Claude Code | Codex CLI | Gemini CLI |
| --- | --- | --- | --- |
| Skill instructions/supporting text | Delimited message section | Delimited message section | Delimited message section, existing JSON prompt encoding |
| Wiki and retrieved context | Bounded message section and captured artifact | Same | Same |
| Profile instructions | Delimited message section at its configuration scope | Same | Same |
| Command recipe | Instruction text; existing shell approval applies | Same | Same |
| Stdio MCP | Per-run MCP JSON added to ambient CLI configuration | Per-run `-c mcp_servers…` overrides | Merged per-run system settings alongside ambient CLI configuration |
| Streamable HTTP MCP | Per-run `type:http` definition | Per-run URL and `env_http_headers` | Per-run `httpUrl` definition |
| MCP tool reference | Parent server supplied; other server tools remain exposed | Same | Same |
| Switched-off MCP tools | `--disallowedTools mcp__pb_<id>__<tool>` | `mcp_servers.pb_<id>.disabled_tools` | `excludeTools` |
| Custom MD file | Delimited message section under its file name | Same | Same |
| Agent profile | Primary agent's tuple; supporting agents as `--agents` subagents | Primary agent; supporting agents kept, reported | Same as Codex |

On legacy staged boards, Planning and Code Review cannot receive Base MCP servers or command recipes; on a pipeline board, neither can its read-only typed Planning and Code Review columns, and every other column can. MCP `readOnlyHint` is not enforcement. Optional incompatible attachments are omitted with an explanation; required ones block. Base does not enable Antigravity for Kanban. No native skill package loading is claimed: scripts in imported skills are reference text and never run automatically.

Writing stages inherit tools, MCP servers, plugins/extensions, and skills through the underlying CLI's normal configuration loading in the task worktree. Base adds its selected per-run MCP definitions and supported subagents; it does not replace that ambient configuration. Claude writing stages omit `--strict-mcp-config`; Gemini writing stages omit extension disabling and the selected-name server allowlist. Codex already inherits its ambient configuration. CLI trust, approval rules, and administrator restrictions still apply and may prevent a configured tool from running. The Base manifest records Base-managed delivery only; it is not an inventory of inherited tools or proof of invocation. Project-scoped CLI configuration must be available in the task worktree; Promptboard does not copy ignored configuration or credential files from another checkout.

Planning and Code Review retain their legacy restrictions: Claude uses an empty strict MCP configuration and limited read tools; Gemini disables extensions, supplies an empty MCP allowlist, and retains the deny policy; Codex retains its read-only sandbox and approval policy. Composer and wiki-generation adapters retain their separate restrictions.

Provider permission modes, hooks, Codex notify, Claude usage status line, Gemini administrator settings, model/effort options, long-prompt paste, the exact card prompt, and required evidence retain their existing paths. Generated configuration stays outside task worktrees. No global, project, or administrator CLI configuration file is changed. Fresh starts and native resumes follow the same inheritance rule. See [Claude CLI flags](https://code.claude.com/docs/en/cli-reference) and [Gemini configuration](https://geminicli.com/docs/reference/configuration/) for native loading and restriction behavior.

Credentials are environment-variable references. Claude and Gemini support reference aliases; Codex stdio delivery requires matching names because its `env_vars` forwards names and embedding resolved aliases in arguments would expose credentials. HTTP header references may include a complete bearer header value in the referenced environment variable. Base never reads CLI credential files, copies credentials, changes provider homes, performs global setup, or grants tool approval. Gemini `trust` remains false.

## Explicit MCP tests

The pinned `@modelcontextprotocol/client` 2.3.1 SDK performs initialization and supported tools/resources/prompts discovery over stdio or Streamable HTTP. Tests need a trusted definition and an explicit action. Stdio discovery executes that definition's program. A small pipe bridge owns its process group and stops descendants when discovery ends; it does not implement MCP or invoke tools. HTTP discovery permits deliberately configured local endpoints, rejects redirects, and does not use CLI OAuth credentials. It needs declared environment headers when authentication is required.

Discovery is bounded by time, message/output sizes and pagination, returns sanitized identities, and closes its connections. No connection test occurs on import, save, attach, or page load. “Supplied” means instructions/context or native configuration were delivered. It does not prove that the model invoked a tool. Observed invocation is a separate fact and is not inferred from attachment.

## Sources and capture

Text/Markdown and supported source files are selected against the run's actual worktree. External roots need explicit approval; each capture checks real paths, symlink containment, excluded secrets/generated paths, file identities, size limits and cancellation. URL documents resolve and pin public DNS addresses on each redirect. Private/local document URLs, credentials and query strings are refused. Local MCP endpoints use their separate explicit connection boundary.

Knowledge uses a bounded hash-cached lexical index, with a per-resource character budget, estimated token counts and omitted-section reporting. Captures keep source references, timestamps and hashes.

A Context resource with `complete: true` (used for chosen [Project Context](origin-project-context.md) sections) is supplied whole or not at all: if any of its material would be omitted for the budget, preparation fails with `BASE_CONTEXT_BUDGET`, which blocks the run when the resource is required. Task text and evidence are preserved. Live sources are captured at launch; their earlier contents and remote model behavior are not claimed to be replayable. Persistent captured context files and the sanitized manifest stay with run evidence. Temporary native configuration is removed on exit or failed preparation.
