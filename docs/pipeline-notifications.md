# Browser column notifications

In an opt-in pipeline, add **Notify me** to a column's exit group or an active column's enter group. Title (500 characters) and body (4,000 characters) support the existing template variables. Saving, task creation in To Do, import and same-column ordering send no alert. The row uses the existing ordered move journal and cancellation; it changes no agent configuration, Composer text, Base selection or CLI tools.

Open **Settings → Desktop notifications → Enable browser notifications**. Only this button requests browser permission. Permission and opt-in belong to the browser and local origin; they are not portable board settings. An already opted-in browser with granted permission reconnects on app load without prompting. Turn off notifications to close its receiver and its owned alerts. After a transport failure, use Reconnect for future alerts. No disconnected or uncertain alert is retried.

The application selects the most recently connected browser receiver for each action, so multiple open windows do not all show the same alert. Each connection gets a new lease; every action gets its own receipt nonce. A replaced, foreign or late acknowledgement cannot finish another receiver's action. Reconnecting does not replay journal entries or hand an unknown display to another window. The server allows eight receivers, 128 pending alerts and 10,000 distinct dispatch IDs per process; browser retention is bounded to 64 open alerts and 10,000 seen IDs. Exhausted limits remain unconfirmed until space is available or a fresh app process/browser page is opened; restarting never replays old journal grants.

Construction and transport acceptance are not display confirmation. The exact browser's native `show` event is acknowledged once and records `succeeded`; this is the browser's display report, not proof that the operating system made an alert visible or that someone read it. Missing permission, unavailable receivers, display errors, early closure, exhausted bounds and no acknowledgement within five seconds record `unconfirmed`. Task Stop cancels only its pending action and closes only that action's owned alert. Already confirmed effects remain recorded. A lost acknowledgement is never retried; its unknown outcome stays unconfirmed.

Clicking an alert focuses the app, selects its project and opens its task Details. It never moves a task, starts an agent or follows a supplied URL. If the task has been removed, the app announces that it is unavailable. Fields are literal notification strings and safe DOM text, with no external images or links. This uses non-persistent notifications while the page is open; no service worker or background push is installed. Browser/OS permission restrictions apply. Some browsers do not support the native display event, so they cannot confirm delivery. See the [Notifications API standard](https://notifications.spec.whatwg.org/) and [browser display-event documentation](https://developer.mozilla.org/en-US/docs/Web/API/Notification/show_event).

`POST /api/notifications/connect` opens an NDJSON stream after explicit consent and granted-permission fields; `POST /api/notifications/ack` accepts only scoped lease/receipt/status fields. Both retain the common loopback Host, Origin, fetch-site and token checks. The token stays in a header, never a URL. Bodies, buffers and acknowledgement time are bounded. Receiver leases/receipt nonces stay in process/browser memory and out of portable backups. Shutdown closes owned streams and settles the existing journal without relaunch or replay.

Verification uses disposable authenticated servers, jsdom and Chrome with the Notification API replaced before page scripts execute. It checks explicit/denied/revoked permission, exact acknowledgements, cancellation, loss, replacement, no replay, literal content, click scope, keyboard controls, both themes and narrow screens. No test requests native desktop permission or creates a real OS alert. Native agent message delivery and explicit automation retries remain separate unfinished parity steps.
