# Durable asynchronous message receipts

The move journal now prepares asynchronous enter-message ownership separately from delivery. A board move can finish after its message has been handed to the session scheduler, while the receipt continues through dispatch, submission, native queue acceptance and conversation confirmation. The [automation coordinator](pipeline-automation-coordinator.md) now supports an optional callback that verifies this exact persisted handoff. Configured deferred enter rows now integrate native scheduling, Board/HTTP/editor controls and durable receipts; see [the current scheduler contract](native-message-scheduler.md). Immediate/exit/slash delivery and explicit retries remain pending. These contracts type no input and leave Composer, Base delivery and inherited CLI tools unchanged; the journal checkpoint did not change the separate board state schema.

New move records use journal version 2. Version 1 records remain readable and finish through their original synchronous APIs without implicit rewriting. An old move cannot acquire asynchronous message ownership; an intentional new request needs new IDs. Older journal readers reject version 2 before granting work. The separate board state schema is unchanged in this checkpoint.

An enabled enter message first receives the existing durable action start grant. `scheduleMessage` then atomically changes its dispatch outcome to `scheduled` and creates a `queued` delivery record. The action's dispatch outcome is immutable and does not claim success. Later enter rows may start in their recorded order, and placement can become complete while the delivery is queued. Exit messages and scripts, webhooks or notifications cannot use this asynchronous handoff. The coordinator verifies callback acknowledgements against the persisted exact message hash, mode and provider/session/run tuple, recognizes scheduled actions as already owned and refuses to replay them. Callers may not advance after a lost save acknowledgement or thrown group error; they must stop and record owned work first.

The delivery captures provider, logical session, process run, immediate/deferred mode and a SHA-256 hash of the rendered literal message. It omits prompt text, history paths, native conversation IDs and credentials. The caller must resolve and validate the exact configuration, message hash, current task content, native session ownership and cancellation before requesting a dispatch grant. Readiness waiting and native input sequencing belong to the scheduler; this journal does not serialize different messages or retarget them to another run.

`startMessageDelivery` grants the queued-to-dispatching change once, including after placement completed. No PTY bytes, escape key or native submission may be sent without an acknowledged grant. `markMessageSubmitted` records the transport attempt and does not prove acceptance. `markMessageAccepted` records native queue ownership only after submission; it does not prove a conversation turn. `finishMessageDelivery` can record confirmation only after submission, using the forthcoming adapter's verified native receipt. Queued or dispatching messages can instead finish failed, cancelled, timed out or unconfirmed. Queue acceptance can also end unconfirmed if a conversation turn is never observed. Timestamps for known earlier stages remain intact.

Receipt outcomes are terminal and immutable. A late confirmation cannot replace cancellation, interruption or uncertainty, and no completed stage can authorize another dispatch. If dispatch publication fails, no input grant is returned. If final receipt publication fails after transport, the submitted marker remains authoritative and cannot grant another send. Unknown outcomes require an explicit new request rather than automatic retries or restart escalation. The scheduler must honour every returned grant and stop/recheck ownership when a save is not acknowledged.

Move cancellation refuses while asynchronous deliveries remain active, even after placement completed. The caller must cancel owned scheduler work and persist each delivery outcome first. Cancellation retains the already applied session lifecycle and confirmed receipts. Recovery checks that the move's application owner is definitely gone and marks unfinished deliveries interrupted without input, process signals or replay. A completed placement retains its completed status and successful lifecycle even when its delivery is interrupted. An unfinished move becomes interrupted through the existing recovery path, preserving known action and delivery results. Live or uncertain owners remain untouched.

All changes use the existing flushed immutable revisions and compare-and-swap publication. Bounded outcome validation rejects raw diagnostics and unknown fields; corrupt or newer records fail closed rather than falling back to queued intent. Receipts share the journal's 1 MiB record and 4,096 revision limits. Polling does not need a persisted revision for every check: the integration should save acknowledged stage changes and final outcomes only.

Tests use disposable journals, actual OS processes and simulated native-format files. They cover nonblocking placement, ordered later rows, competing dispatch grants, distinct stages, private native receipt integration, scope capture, duplicate/stale acknowledgements, cancellation, every restart phase, completed versus unfinished placement, live owners, version 1 compatibility, corrupt/newer records and publication failures. No live agent, external webhook or desktop notification is used. Runtime deferred session selection/readiness, native input and durable receipt display are now integrated. Immediate/exit/slash delivery and explicit retry UI remain pending.
