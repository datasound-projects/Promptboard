# Automation execution primitives

`PipelineActions` supplies execution for scripts, webhooks and notifications. The [column runtime](pipeline-runtime-automations.md) now connects scripts/webhooks to journaled board moves. Configuration reads, imports and Composer never call it. Agent messages require their separate session scheduler; notification reception and the row editor remain pending. In-memory duplicate protection does not replace durable recovery or authorize replay after restart.

Scripts run a private temporary file through `/bin/sh` on POSIX or Windows PowerShell's `-File` option on Windows. There is no secondary `cmd.exe` parsing and no execution-policy change. The caller must supply the verified task worktree or project checkout. Script templates use the existing stripped substitutions; exact values arrive separately in `PROMPTBOARD_*` environment variables. Use quoted environment expansion rather than evaluating that text. Windows scripts use PowerShell syntax and an explicit `exit` when they need to report a particular native command's exit code. The configured timeout defaults to ten minutes; the move runner can supply a shorter remaining exit budget. Output is ignored, so chatty scripts cannot fill an unread pipe. Outcomes include the actual exit code; raw diagnostics and script content are not returned.

Cancellation/deadline termination targets only the script's owned process group on POSIX or its process tree with Windows `taskkill /T /F`. Execution waits for closure and bounded termination cleanup (up to seven seconds for the Windows helper); an unconfirmed stop is a failure rather than invented success. A still-live root remains owned and addressable for Cancel/shutdown instead of being killed alone and orphaning its descendants. Concurrent actions retain separate cancellation. Shutdown stops this runner's jobs. Temporary files use the existing owned-directory registry so failed removal can be retried during app cleanup without replacing the action's execution outcome. Native environment limits can reject large task metadata; values are not silently truncated to make a process launch.

Webhooks have one thirty-second total budget, including waits and up to three attempts. Only transport errors, 408, 429 and 5xx permit retries. `Retry-After` accepts seconds or an HTTP date within that budget. Every request carries the same persisted action ID as `Idempotency-Key`; receivers can use it to deduplicate. An optional attempt callback must finish before transport starts, allowing the journal to save each attempt first. Cancellation or a failed/timed-out callback prevents the next request. Redirects are recorded as failures. GET carries no body. An empty body uses the task/move/project envelope without its description; a custom body uses JSON-escaped substitutions. URL and header outputs are capped at 8 KiB, bodies at 2 MiB, and rendered line breaks in headers are rejected. Responses contribute their status, not raw body text or authentication headers.

Notifications pass literal rendered title/body, persisted action ID and project/task identity to an injected receiver. Title/body are capped at 500/4,000 characters. Only an explicit receiver acknowledgement records success; a missing receiver or absent acknowledgement records `unconfirmed`. A cancelled or timed-out receiver is not retried here. Browser permission handling, task-click navigation, failure toasts and the durable log belong to the forthcoming integration.

Each accepted action owns a referenced deadline timer and clears it when its outcome resolves. Pending callbacks therefore reach their bounded timeout even in a standalone Node 22 process without other I/O; no test keep-alive interval is needed.

Tests exercise native script files in quoted working directories, exact environment values, large output, nonzero exits, missing paths, owned child-tree cancellation, independent jobs, shutdown, deadlines, real loopback HTTP receivers, JSON/URL/header boundaries, bounded retries, dates, intent persistence failures and unconfirmed notifications. Windows behavior must pass the GitHub matrix before merge. No real external webhook or desktop notification is sent by these fixtures.
