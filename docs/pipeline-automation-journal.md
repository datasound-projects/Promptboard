# Durable automation move journal

`PipelineJournal` prepares the durable intent and outcome layer for column automations. The [column runtime](pipeline-runtime-automations.md) now connects it to `Board.transition`, scoped startup recovery and authenticated receipt endpoints for scripts/webhooks. Native message scheduling, notification reception and the editor remain pending. State version 6 records task-scoped move ownership while preserving Composer, Base and native CLI configuration.

New records now use version 2 and prepare [asynchronous enter-message receipts](pipeline-message-journal.md). Their immutable `scheduled` dispatch outcome releases later rows and placement without claiming delivery success; a separate nested receipt remains observable and recoverable after the move completes. Version 1 records remain readable under their original synchronous contract. The ordering and cancellation descriptions below apply to synchronous rows; active asynchronous receipts must also be stopped and recorded before move cancellation.

One move is identified by project, task and transition IDs, independently of the task's bounded transition history. Reusing those IDs returns the original record even after later moves or configuration edits. An intentional retry needs a new transition ID and new action IDs; the forthcoming scheduler must validate current task/configuration before constructing it. No journal API executes work or automatically retries a move.

Records live under `<dataDir>/automations/<SHA-256 identity>/`, separately from board state. Each update writes and flushes a private temporary file, then publishes it as the next immutable numbered revision using a hard link. Competing writers cannot overwrite that filename. A losing writer rereads the winner; only a successful pending-to-running publication grants execution. This applies to actions and to the session lifecycle. There is no rename-overwrite fallback on filesystems that cannot create hard links. Those filesystems fail closed before a grant. Directory metadata is flushed where the platform supports it; power-loss guarantees remain dependent on the operating system and storage device. Partial unpublished temporary files are ignored.

The order is source exit rows, session lifecycle, destination enter rows. Enabled rows begin pending; disabled rows are recorded as skipped. The journal permits a start only in the current phase after earlier dispatch outcomes finish. Exit failures do not prevent advancing to the lifecycle. A failed/cancelled lifecycle skips destination rows. A completed move can contain failed, unconfirmed or scheduled automations: its individual outcomes remain visible rather than being replaced by a successful move status. Callers must check the returned start grant and cancellation before invoking an adapter.

Webhook attempt 1, 2 and 3 each require a new persisted receipt while the action is running. Duplicate attempts are refused, so they cannot authorize another request. The action ID is the receiver's stable idempotency key. `PipelineActions` can use `recordAttempt` as its existing pre-transport callback; the integration test verifies the saved receipt before every simulated request. Receiver-side idempotency is still necessary: an unknown transport outcome is not proof that a remote side effect did not occur.

Terminal outcomes are immutable through this API. A late success acknowledgement cannot replace failure, cancellation or interruption. If a final save fails, the earlier running marker remains authoritative and cannot grant a second start. Corrupt, missing or newer revisions block reads/changes; they never fall back to an earlier pending record. Reads and listings do not create directories or repair records.

Explicit move cancellation refuses while an action or lifecycle is still running. The caller must stop owned work and record its outcome first. Cancellation then skips remaining pending effects and preserves confirmed outcomes, including a session lifecycle that already succeeded. Repeating cancellation grants no work.

Moves retain their owning application PID (for diagnostics), a random per-process instance ID and a lease (`leaseId`, `heartbeatAt`, `leaseExpiresAt`). Another process cannot execute or finish their actions. A lease lasts 60 seconds. While a move is unfinished, including a pending message delivery, the owning journal renews it about every 20 seconds through the same compare-and-swap revision write. Renewal stops when the move completes, is cancelled or recovered, and on shutdown; its timers never keep the process running. Each renewal is one revision, so the 4,096-revision cap allows about 22 hours of continuous ownership per move.

Recovery of a leased move depends only on the lease. An operating system can give an old PID to an unrelated process, so a live PID cannot keep a move; an unexpired lease of another process always blocks recovery. A crashed process therefore keeps its move for at most one lease period. Board retries such moves on its once-per-second follow-up tick and recovers them without user action. Until then, **Stop automations** refuses with `AUTOMATION_OWNER_ACTIVE` and names the lease expiry. Recovery also replaces the lease ID. An expired lease that no process recovered stays with its owner, for example after the computer slept: its next write or renewal wins or loses the same compare-and-swap. An owner whose lease ID was replaced gets `AUTOMATION_LEASE_LOST`. It stops renewing, Board stops that move's owned script and message work, and nothing is replayed; the card shows blocked until **Stop automations** confirms cleanup.

Records without lease fields, written by older versions, keep the earlier rule. A later process with the same PID is not the owner: it sees a different instance ID and treats the earlier owner as gone. Records without an instance ID keep the PID-only check; if PID reuse or access restrictions make liveness uncertain, recovery leaves such a record alone. Explicit recovery checks that the owner is gone, then marks unfinished rows and lifecycle work interrupted in one atomic revision, preserving confirmed outcomes and original start times. Recovery does not touch live owners, kill processes, run actions or replay moves.

Stored metadata includes column identities, task/project revisions, row identities/names/types, configuration hashes, timestamps, bounded outcome fields and webhook attempt receipts. It omits executable scripts, message bodies, URLs, authentication headers and task descriptions. Callers must supply safe user-facing reasons rather than raw provider/network diagnostics. Each record is capped at 1 MiB; a move allows at most 80 rows and 4,096 immutable revisions. Records are not automatically pruned, so old request IDs remain deduplicated. Retention/export and board-backup handling remain integration work.

Tests cover concurrent instances and real OS processes, durable start grants, ordered phases, exit/lifecycle failures, stale acknowledgements, all restart phases, live-owner protection, lease renewal, expiry and loss with reused PIDs, legacy PID-only records, old duplicate requests, invalid identities, unavailable storage, partial/corrupt/newer revisions, bounded outcomes and persisted webhook attempts. They use disposable storage and fake transport; no actual agent, external webhook or notification runs.

Implementation uses the [Node filesystem API](https://nodejs.org/docs/latest-v22.x/api/fs.html). The behavioral reference is [Kangentic columns and automations](https://www.kangentic.com/features/workflows/). Runtime scheduling, message delivery, notifications, explicit retry UI and enabling automation rows remain pending.
