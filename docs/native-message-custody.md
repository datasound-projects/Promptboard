# Live native receipt ownership

The Supervisor now connects the [native receipt reader](native-message-receipts.md) to its owned pipeline sessions through internal `checkpointMessage`, `verifyMessage` and `cancelMessageCheckpoint` methods. They prepare and inspect evidence without typing automation input. They are not HTTP endpoints, and their opaque tickets cannot be serialized or recreated. Message scheduling, durable receipt updates, delivery controls and enabled automation rows remain pending. Composer, Base, inherited CLI tools and application state version 5 are unchanged.

Each checkpoint belongs to one Supervisor instance, process run, actual PTY object and observed native conversation. Before checking evidence, the Supervisor flushes its existing lifecycle reader. Missing, partial or malformed lifecycle evidence cannot authorize a checkpoint or confirmation. Main startup changes the input epoch even when the native conversation ID stays the same; subordinate events cannot redirect the parent's history. A changed native ID requires a reader for that exact conversation. Matching late records cannot revive revoked tickets.

Every nonempty manual terminal write changes the epoch before writing, including a partial draft and a write whose transport fails. The initial long-prompt bracketed paste and its submission also change the epoch. Process replacement, removal, exit, Stop/Pause intent, launch failure, shutdown, ended activity and uncertain observations revoke evidence. Owned process signalling and exit close the reader before asynchronous teardown. None of these changes retries or modifies input.

Claude and Gemini use the main hook's reported absolute transcript path and observed native ID. The strict reader still checks filename, regular file, format and exact conversation identity; the hook path alone is insufficient. Gemini's `transcript_path` avoids guessing its project storage directory. Codex uses the exact-thread rollout selected by the existing usage locator, then independently validates the native metadata and content. That locator currently searches the run's start date and the current date. An older resumed Codex history outside those dates remains unavailable here; persistent verified history locations and bounded older-history discovery are still needed. No timestamp-nearest or unrelated file fallback is used.

History paths and readers remain in process memory. Public run updates and receipt results omit transcript paths and conversation content. Claude queue acceptance remains distinct from conversation confirmation. A checkpoint is evidence only: it neither proves native readiness nor grants a terminal write. The forthcoming scheduler must serialize deliveries, validate current task/configuration, persist its dispatch grant, honour cancellation and verify actual transport text. These observations cannot authorize plan approval, permissions, cleanup or merging.

Tests use controlled PTY seams, disposable native-format files and actual simulated Claude/Gemini PTYs in disposable repositories. They cover all three providers, exact new messages, queue acceptance, partial human drafts, main/subordinate starts, conversation changes, cancelled/replaced/uncertain ownership, absent lifecycle files, opaque tickets, and real owned-process teardown. They send no automation input and exercise no authenticated live-provider session.

Provider path evidence: [Claude hook input](https://code.claude.com/docs/en/hooks) and [Gemini common hook fields](https://geminicli.com/docs/hooks/reference/). Native record validation retains the pinned format references in the receipt-reader documentation.
